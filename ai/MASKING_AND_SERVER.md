# 마스킹과 AI 서버 처리 설계

점검 사진이 휴대폰에서 가려지고, 서버에서 저장 전 확인을 거쳐 저장되고, AI 판독을 거쳐 결과로 나가기까지의 처리 방식을 정리한 문서입니다. 코드 위치와 설정 값, 실패했을 때의 동작, 검증 현황과 시범 운영 전에 남은 일을 함께 적었습니다.

## 1. 전체 흐름

**앱 마스킹 + 서버 저장 전 확인** 구조입니다. 서버에는 앱이 가린 사진만 들어오고, "가린 사진만 들어온다"는 원칙은 앱 마스킹이 지킵니다. 서버의 확인은 앱이 혹시 놓친 것이 저장소·판독 모델·담당자 화면으로 퍼지지 않게 막는 안전망입니다. 앱 쪽 처리(회전 보정, 메타데이터 제거, 얼굴·번호판 가림, 원본 삭제)는 `contract/APP_MASKING_GUIDE.md`에 있고, 아래는 서버 쪽 처리입니다.

| 단계 | 하는 일 | 코드 | 실패하면 |
|---|---|---|---|
| 0 앱 | 휴대폰에서 가린 사진만 `device_masked=true`와 가림 보고를 붙여 전송 | 앱 | 전송하지 않고 다시 찍기 |
| 1 받기 | JPEG/PNG·15MB 이하인지 확인, 휴대폰 회전 정보 반영, 메타데이터(GPS 등) 제거 | `images.decode_upload` | `error` + 다시 찍기 |
| 2 품질 확인 | 흐림·어두움 | `quality.check_array` | `retake` (저장·AI 없음) |
| 3 저장 전 확인 | 받은 (이미 가린) 사진에 알아볼 수 있는 얼굴·번호판이 남았는지 확인하고, 남았으면 저장·AI 판독 전에 가린 뒤 그 수를 `server_added`로 기록 (0이 정상). 앱 마스킹이 없는 시험 단계에서는 이 단계가 마스킹을 맡음 | `privacy.mask_image`, `pipeline.ingest` | `error` + 다시 찍기 (저장·AI 없음) |
| 4 축소·저장 | 긴 변 1568px로 줄여 메타데이터 없는 JPEG로 저장 | `images`, `storage.save_masked` | 서버 오류 |
| 5 AI 판독 | 가린 사진만 전송, 동시 호출 제한 | `jobs.ai_gate`, `providers/` | `needs_review` + 나중에 재판독 |
| 6 2차 확인 | AI가 알려 준 가림 누락을 다시 가림, 가림 영역과 문제 위치 겹침 확인 | `pipeline._remask_leaks` | — |
| 7 등급·결과 | 규칙으로 등급 계산, 결과 저장. 업무 시스템은 등급을 쓰지 않음(계약서 참고) | `rules`, `storage.LocalResultStore` | — |

운영에서 원본은 휴대폰 밖으로 나가지 않습니다. 개발 단계처럼 서버가 1차로 가리는 경우에도, 받은 사진은 1~3단계 동안 서버 메모리에만 있고 3단계가 끝나면 참조를 버립니다. 디스크에 쓰이는 것은 4단계의 가린 사진과 7단계의 결과 JSON뿐입니다.

## 2. 개인정보 원칙

0. **원본은 휴대폰 밖으로 내보내지 않습니다.** 앱이 가린 사진만 보냅니다. 운영 서버는 `REQUIRE_DEVICE_MASKING=1`로 가리지 않은 사진을 받지 않습니다.
1. **서버도 원본을 저장하지 않습니다.** 서버 코드에 원본을 디스크에 쓰는 경로가 없습니다. 업로드 임시 버퍼도 읽자마자 닫아서 지웁니다.
2. **가리지 못하면 내보내지 않습니다(fail-closed).** 검출기나 가림 처리에서 오류가 나면 저장도, AI 전송도 하지 않고 다시 찍어 달라고 안내합니다.
3. **AI에는 가린 사진만 보냅니다.** 판독은 자체 서버의 공개 모델(Ollama)로만 하고 사진을 외부 AI 업체로 보내지 않습니다(2026-10-11 결정).
4. **메타데이터를 남기지 않습니다.** 사진 파일 안의 GPS·기기 정보는 1단계에서 사라지고, 저장하는 JPEG에도 넣지 않습니다. 촬영 위치는 사진 파일이 아니라 별도 필드로 다룹니다. 업무 연동에서는 백엔드가 시설 대장으로 위치 태그를 정해 넘깁니다.
5. **놓친 것은 퍼지기 전에 막고 기록합니다.** 서버의 저장 전 확인이 앱이 놓친 것을 찾으면(`server_added`), 또는 AI가 아직 알아볼 수 있는 얼굴·번호판을 보고하면(`leaks_fixed`) 가리고 기록해 검출기 개선 자료로 씁니다.
6. **사람이 표본으로 점검합니다.** 담당자는 `GET /audit/masking`이 고른 표본(누락 보정 이력이 있는 사진 전부 + 무작위)을 눈으로 확인합니다. 가림이 부족하다고 기록하면 그 사진은 내려주지 않습니다(410).

## 3. 마스킹

### 3.1 처리 순서와 그 이유

1. **회전 보정을 먼저 합니다.** 휴대폰 사진은 픽셀은 누워 있고 회전 정보만 붙어 있는 경우가 많습니다. 보정 없이 검출하면 옆으로 누운 얼굴을 찾게 되어 검출률이 크게 떨어집니다.
2. **원본 해상도에서 찾습니다.** 축소한 뒤에 찾으면 멀리 있는 작은 얼굴과 번호판을 놓칩니다. 다만 너무 큰 사진은 속도를 위해 긴 변 2,400px(`DETECT_MAX_SIDE`)까지 줄여서 찾고, 좌표는 원본 크기로 되돌려 가립니다.
3. **가린 뒤에 줄입니다.** 저장과 AI 전송에는 긴 변 1,568px이면 충분합니다.

### 3.2 얼굴 검출

- **기본: YuNet.** `models/face_yunet_s.onnx`(BSD-3)를 쓰고, OpenCV 내장 `FaceDetectorYN`으로 실행해 별도 라이브러리가 필요 없습니다. 기준 점수는 0.55(`FACE_SCORE`)입니다. 놓치는 것이 더 위험하므로 일반적인 0.6~0.9보다 낮게 잡았습니다.
- **대체: Haar.** 모델 파일이 없을 때만 OpenCV 기본 Haar(정면 + 좌우 측면)로 동작합니다. 이때 `/health`와 로그, 결과의 `meta.privacy.detectors.face`에 `haar(대체)`가 표시됩니다. 운영에서는 이 상태가 되지 않게 배포 점검 항목에 넣습니다.

### 3.3 번호판 검출

세 가지 검출기와 차량 안전망을 함께 돌려, 하나라도 찾은 곳을 모두 가립니다.

- **사전 학습 번호판 모델 (기본):** open-image-models의 YOLOv9 번호판 검출기(MIT)입니다. 여러 나라 번호판으로 이미 학습돼 있어 따로 학습하지 않고 바로 씁니다. 기준값을 0.15로 낮춰 놓치는 쪽보다 더 가리는 쪽으로 맞췄습니다.
- **규칙 기반 검출기:** 글자 획이 촘촘한 가로 띠, 사각형 윤곽, 주변보다 밝은 판에서 후보를 모은 뒤 글자 모양 덩어리를 확인합니다. 간판이나 버스 글자를 번호판으로 보고 가리는 경우가 있지만, 더 가리는 쪽이라 둡니다.
- **차량 안전망:** 사전 학습 물체 검출기(RF-DETR, COCO)로 자동차·버스·트럭·오토바이를 찾습니다. 그 안에서 번호판을 하나도 못 찾았으면 차량 전체를 거칠게 뭉갭니다. 점검 사진에서 차량은 배경이라 가려도 판독에 지장이 적습니다. 차의 크기·방향과 관계없이 적용합니다. 검출기는 "옆모습이라 번호판이 원래 없음"과 "번호판을 놓침"을 구분하지 못하므로, 옆모습 차와 멀리 작게 찍힌 차도 가립니다. 앱 마스킹 안내(`contract/APP_MASKING_GUIDE.md`)와 같은 규칙입니다.
- **추가 학습 모델 자리:** 실제 한국 사진 평가가 기준에 못 미치면 `PLATE_MODEL`에 추가 학습한 모델을 넣습니다(4장).

**지금까지 확인한 것**
- 합성 한국 번호판 80장: 규칙 기반만 쓸 때 44% → 사전 학습 모델을 더하면 60%. 합성 번호판은 차가 없는 엉뚱한 배경에 붙인 것이라 학습 모델에 불리한 시험이며, 차량 안전망은 이 시험에서 효과가 드러나지 않습니다.
- 실제 차량 사진 1장(외국 번호판): 주차된 차의 번호판은 사전 학습 모델이 찾아 덮었고, 번호판을 못 찾은 뒤쪽 차량들은 차량 안전망이 통째로 뭉갰습니다.
- **판단은 실제 한국 사진으로 해야 합니다.** 시범 구역에서 차가 보이는 사진으로 `run_mask_eval.py`를 돌려 4장의 기준을 확인합니다.

### 3.4 가리는 방법

| 대상 | 방법 | 이유 |
|---|---|---|
| 얼굴 | 가로 6칸 정도의 거친 모자이크 + 흐림, 상자 25% 확장 | 약한 흐림·잘게 나눈 모자이크는 복원 시도가 가능하므로 정보를 충분히 뭉갭니다 |
| 번호판 | 회색 단색으로 덮음, 상자 20% 확장 | 글자는 모자이크로도 추정될 수 있어 아예 지웁니다 |

### 3.5 2차 안전장치: AI의 누락 보고

판독 프롬프트에 "가린 뒤에도 알아볼 수 있는 얼굴·번호판이 있으면 위치를 적으라"는 항목이 있습니다(`privacy_leaks`). 보고가 오면 다음처럼 처리합니다.
- 저장된 사진의 그 자리를 다시 가려 덮어씁니다.
- `meta.privacy.leaks_fixed`에 개수를 남기고, 경고 로그를 씁니다.

**이 장치의 한계:** 누락된 부분은 이미 판독 모델에 전달된 뒤에 발견됩니다. 자체 서버라 사진이 밖으로 나가지는 않지만, 모델 입력과 판독 기록에는 이미 들어간 뒤입니다. 그래서 이것은 저장본과 담당자 화면을 지키고 검출기 약점을 찾는 보조 장치일 뿐이며, 1차 검출기 성능을 대신하지 못합니다.

### 3.6 판독 보호

가림이 시설의 문제 부위를 덮으면 판독이 틀릴 수 있습니다.
- AI가 지목한 문제 위치가 가림 영역과 25% 이상 겹치면 담당자 확인(`needs_review`)으로 보냅니다.
- 사진의 30% 이상이 가려지면 메모를 남깁니다.

### 3.7 처리 시간 (측정값)

4032×3024 사진, CPU 1개 기준입니다. 아래는 얼굴·규칙 기반 번호판만 쓸 때이며, 사전 학습 번호판 모델과 차량 검출을 더하면 사진 한 장에 약 1~1.5초가 더 걸립니다(작은 실제 사진 기준 1.2~1.6초 측정).

| 검출 해상도(`DETECT_MAX_SIDE`) | 마스킹 전체 |
|---|---|
| 2,400px | 0.85초 |
| 1,600px | 0.42초 |

## 4. 번호판 검출 모델 추가 학습 (필요할 때만)

사전 학습 모델과 차량 안전망으로 실제 사진 평가 기준을 넘으면 이 장은 건너뜁니다. 못 넘으면 사전 학습 모델에서 출발해 한국 사진으로 추가 학습합니다. 처음부터 학습할 때보다 훨씬 적은 사진(100~300장)으로 충분합니다.

**1. 데이터**
- AI Hub에서 차량 번호판이 포함된 데이터셋을 찾아 이용 조건을 확인합니다.
- 시범 구역에서 직접 찍은 사진 300장 이상에 번호판 상자를 표시해 섞습니다. 보도 쪽에서 비스듬히 찍힌 번호판, 멀리 있는 작은 번호판이 실제 상황입니다.

**2. 모델**
- 클래스 1개(plate)짜리 소형 검출 모델을 학습합니다. 입력은 640 또는 960입니다.

**3. 라이선스 확인**
- Ultralytics YOLO는 AGPL-3.0입니다. 시 시스템에 넣을 때는 라이선스 검토가 필요합니다.
- Apache-2.0 계열(YOLOX 등)로 학습할 수도 있습니다. 다만 출력 형식이 다르면 `privacy.decode_yolo`에 맞춰 변환 함수를 추가해야 합니다.

**4. 내보내기와 연결**
- ONNX로 내보내 `models/plate_ko.onnx`에 두고, `PLATE_MODEL=models/plate_ko.onnx`를 설정합니다.
- 지금 코드는 YOLOv8 형식 출력 `(1, 5, N)`을 읽습니다.

**5. 통과 기준**
`eval/privacy/run_mask_eval.py`로 실제 라벨 사진을 평가합니다.

| 지표 | 기준 |
|---|---|
| 번호판 가림 성공률 | 98% 이상 |
| 얼굴 가림 성공률 | 98% 이상 |
| 과잉 가림 면적 평균 | 2% 이하 |
| 사진당 처리 시간 | 1.5초 이하 |

## 5. AI 서버 처리

### 5.1 엔드포인트와 응답 시간 목표

엔드포인트 목록, 응답 시간 목표, 필드 설명은 `contract/API_CONTRACT.md` 한 곳에서 관리합니다(두 문서가 어긋나지 않도록 여기에는 다시 적지 않습니다). 마스킹과 관련된 입구만 요약하면, 판독 사진은 `POST /analyze`·`/verify`에서, 판독하지 않는 참고·보수 사진은 `POST /privacy/mask`에서 같은 검출기로 가립니다. 응답 뒤에 다시 가리거나 보류한 사실은 `image_revision`과 `GET /events`로 업무 백엔드에 전달됩니다.

### 5.2 동시 호출 제한

판독 모델은 한꺼번에 많이 부르면 모두 느려집니다. 자체 GPU 서버는 동시에 처리할 수 있는 양이 정해져 있습니다. `jobs.AIGate`가 이를 관리합니다.
- 동시 호출을 4개(`MAX_CONCURRENT_AI`)로 묶습니다.
- 자리가 나기를 5초(`AI_QUEUE_WAIT_S`) 넘게 기다려야 하면 바로 담당자 확인으로 돌려줍니다. 어르신이 현장에서 오래 기다리지 않게 하기 위해서입니다.

### 5.3 시간 제한과 재판독

1. AI 호출 한 번은 최대 12초(`AI_TIMEOUT_S`)까지 기다립니다. 그 자리에서 재시도하지 않습니다. 기다리는 시간이 최악이어도 자리 대기 5초 + 호출 12초 안에 끝나게 하기 위해서입니다. 운영 모델 `qwen3-vl:8b-instruct`는 GPU에 미리 올려 두면 장당 2~10초라 이 안에 들어옵니다. 그래서 활동 전에 모델을 미리 올리고, 활동 중에 내려가지 않게 합니다([AI 실행 가이드](../docs/AI_실행_가이드.md) 4.2·4.6절).
2. 실패하거나 혼잡하면 즉시 `needs_review`로 응답하고, 응답의 `retry`에 다음 시도 시각을 넣습니다. 업무 백엔드는 이를 담당자 검토로 넘기고 어르신에게 다음 장소를 안내합니다. 어르신 화면 문구는 업무 백엔드가 정합니다.
3. `jobs.RetryQueue`가 **저장된 가린 사진으로** 30초, 2분, 10분 뒤에 다시 판독합니다. 원본이 필요 없으므로 개인정보 원칙과 충돌하지 않습니다.
4. 성공하면 결과 저장소가 갱신되고, `GET /results/{photo_id}`에 최신 등급이 나옵니다. 세 번 모두 실패하면 `retry.gave_up=true`로 담당자 확인에 남깁니다.
5. 서버가 다시 켜지면 저장소에서 대기 중인 건을 찾아 이어서 처리합니다.

재판독으로 결과가 바뀌면 `GET /events`에 `result_updated`가 남습니다. 백엔드는 이 알림을 받아 `GET /results/{photo_id}`로 새 결과를 가져와 결과 스냅샷을 추가하고 검토 분류를 갱신합니다. 업무 시스템은 등급을 쓰지 않으므로 등급에 따른 알림은 보내지 않습니다. 재판독할 사진·맥락이 사라졌거나 재판독 중 오류가 반복되면 대기를 끝내고 `retry.gave_up: true`, `retry.reason`과 함께 담당자 확인으로 둡니다. 서버가 다시 켜지면 결과 파일에서 대기 건을 찾아 원래 예정 시각대로 이어 갑니다.

### 5.4 같은 사진의 중복 요청

전파가 약하면 같은 사진이 다시 올라올 수 있습니다.
- 백엔드가 AI 호출마다 새 `photo_id`를 만들어 보내면, 같은 ID의 두 번째 요청에는 저장된 결과를 그대로 돌려줍니다(`meta.replayed=true`).
- 그래서 판독을 두 번 하지 않고, 같은 사진이 담당자 검토 목록에 두 번 오르지 않습니다.
- 흐림·오류처럼 저장된 것이 없는 경우에는 같은 ID로 다시 찍어도 새로 처리합니다.

### 5.5 보안

- **인증:** `API_KEYS`를 설정하면 `/health`를 뺀 모든 요청에 `X-API-Key`가 필요합니다. 비워 두면 개발 모드이며, 시작 로그에 경고가 뜹니다.
- **업로드 제한:** 15MB, JPEG/PNG, 4,000만 화소 이하만 받습니다. 압축 폭탄과 엉뚱한 파일을 막습니다.
- **사진 주소:** `/images`도 API 키가 필요합니다. 담당자 웹 화면에서 `<img>`로 바로 띄우려면, 운영 단계에서 짧게 유효한 서명 주소 방식으로 바꿔야 합니다.
- **경로 조작:** `photo_id`는 영문·숫자·`_`·`-`만 허용하고, 그 밖의 값은 새 ID로 바꿉니다.

### 5.6 로그

| 남기는 것 | 남기지 않는 것 |
|---|---|
| `photo_id`, 상태, 등급·처리 방침, 가린 얼굴·번호판 수, 누락 재가림 수, 처리 시간, 오류 종류 | 사진, 정확한 촬영 좌표, AI에 보낸 내용 |

### 5.7 배포

- `Dockerfile`로 컨테이너를 만듭니다. 가린 사진(`data/images`)과 결과(`data/results`)는 컨테이너 밖 볼륨에 둡니다.
- 작업자는 1개입니다. 재판독 대기열과 변경 알림 순번이 프로세스 안에 있기 때문입니다. 사용량이 늘면 대기열과 저장소를 외부(Redis, 객체 저장소)로 옮기고 작업자를 늘립니다. `storage.py`와 `jobs.py`만 바꾸면 되도록 나눠 두었습니다.
- 운영은 자체 GPU 서버에서 공개 모델(Ollama)로 판독하고, 비용을 줄이기 위해 활동 시간에만 서버를 켭니다. 켜고 끄는 순서와 모델 미리 올리기는 [AI 실행 가이드](../docs/AI_실행_가이드.md) 4.6절을 따릅니다.
- 설정 값 전체는 `.env.example`에 있습니다.

## 6. 검증 현황

**자동 테스트 65개 (`python -m pytest -q`)**
- **마스킹 (`tests/test_privacy.py`):** 회전 보정과 GPS 제거, 잘못된 파일 거절, YuNet 사용 여부, 얼굴 모자이크·번호판 단색 처리, 고해상도 검출, 마스킹 실패 시 저장·AI 차단, AI 누락 보고 후 재가림, 가림 영역과 문제 위치 겹침 시 담당자 확인, YOLO 출력 해석
- **저장 원칙 (`tests/test_storage.py`):** 가린 사진 하나만 저장되는지, AI에 보낸 사진과 저장된 사진이 같은지, 경로 조작 차단
- **서버 처리 (`tests/test_server_ops.py`):** 같은 `photo_id` 1회 처리, AI 오류 후 재판독 성공, 혼잡 시 빠른 응답, 재시도 한도, API 키 인증, 결과 조회
- **앱 1차 마스킹·활동 기록 (`tests/test_activity.py`):** 앱 가림 보고 기록, 앱이 놓친 것을 서버가 저장 전에 가리고 수를 셈, 운영 모드에서 가리지 않은 사진 거절, 참여자 활동 실적, 시설 이력, 주간 우선 처리 목록, 표본 점검과 보류 처리

**검출기 점검**
- 얼굴: 공개 샘플 사진 2장에서 모두 가림 (작은 얼굴 30px 포함)
- 번호판: 합성 80장 중 60% (사전 학습 모델 + 규칙 기반), 실제 차량 사진 1장에서 번호판과 다른 차량 모두 가림 (3.3 참고)

**시범 운영 전에 반드시 할 평가**
시범 구역 실제 사진 300장 이상에 얼굴·번호판을 라벨링하고, `run_mask_eval.py`로 4장의 통과 기준을 확인합니다. 결과는 발표 자료의 개인정보 보호 근거로도 씁니다.
