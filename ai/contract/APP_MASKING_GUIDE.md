# 앱 마스킹 구현 안내서 (시니어 PWA)

시니어 앱은 PWA(브라우저에서 실행하는 웹 앱)입니다. 이 문서는 사진의 얼굴과 차량 번호판을 **휴대폰 브라우저 안에서 먼저 가린 뒤** 가린 사진만 업무 백엔드로 보내기 위한 구현 기준입니다. 앱은 AI 판독 모듈을 직접 부르지 않고 업무 백엔드 API로 사진을 올립니다. 백엔드가 그 사진을 AI로 넘깁니다.

**"서버에는 가린 사진만 들어온다"는 원칙은 앱 마스킹이 지킵니다.** AI 모듈은 받은 사진을 저장하기 전에 가림 상태를 한 번 더 확인하고, 혹시 남은 부분이 있으면 저장·판독 전에 가립니다. 이 확인은 놓친 것이 퍼지지 않게 막는 안전망이고, AI가 가린 수(`server_added`)는 앱 마스킹 성능을 재는 기록이 됩니다. 0이 정상입니다. 다만 지금 서버는 이미 가린 영역 안에서도 얼굴을 다시 찾아 세므로 값이 실제보다 큽니다(6장 끝 참고).

이 안내서대로 만든 시험용 앱이 있습니다: PWA는 [tools/ai-verify/pwa](../../tools/ai-verify/pwa/README.md), React Native(Expo, iOS·Android) 시험용 앱은 [tools/ai-test-app](../../tools/ai-test-app/README.md). 실기기 시험에서 확인한 내용은 9장에 모았습니다.

## 1. 촬영부터 전송까지

1. **앱 안 카메라로 찍습니다.** `getUserMedia`로 후면 카메라 화면을 앱 안에 띄우고, 촬영 버튼을 누르면 그 순간의 화면을 캔버스에 그려 사진으로 씁니다(2장). 사진이 휴대폰 갤러리에 저장되지 않습니다.
2. **얼굴·번호판·차량을 찾습니다** (3장). 찍은 해상도 그대로에서 찾습니다. 긴 변이 2,400px보다 크면 그 크기로 줄여서 찾고, 좌표는 원래 크기로 되돌립니다.
3. **가립니다** (4장).
4. **긴 변 1,568px로 줄여 JPEG로 만듭니다.** 캔버스에서 `toBlob('image/jpeg')`로 만들면 GPS·기기 정보 같은 메타데이터가 들어가지 않습니다. 위치는 사진 파일이 아니라 업무 API의 위치 필드로 따로 보냅니다.
5. **원본을 버립니다** (5장).
6. **업무 백엔드로 전송합니다** (6장). 통신이 안 되면 가린 사진만 기기에 보관했다가 다시 보냅니다.

**실패하면 보내지 않습니다.** 모델을 불러오지 못했거나 검출·가림 중 오류가 나면 사진을 보내지 말고 버린 뒤 "한 번 더 찍어 주세요"를 띄웁니다. 계속 실패하면 담당자에게 연락하도록 안내합니다. 가리지 못한 사진이 전송되거나 저장되는 경로가 없어야 합니다.

## 2. 카메라

| 항목 | 기준 |
|---|---|
| 방식 | `navigator.mediaDevices.getUserMedia({video: {facingMode: "environment", width: {ideal: 1920}, height: {ideal: 1080}}})`로 앱 안에 카메라 화면을 띄우고, 촬영 순간의 화면을 `<canvas>`에 그림 |
| 쓰지 않는 방식 | `<input type="file" capture>`. 휴대폰 기본 카메라 앱이 열리고, 기종에 따라 원본이 갤러리에 저장될 수 있어 원칙을 보장할 수 없음. 갤러리에서 사진 고르기 기능도 두지 않음 |
| 해상도 | 브라우저 카메라 화면은 기본 카메라 앱보다 해상도가 낮을 수 있음. AI가 긴 변 1,568px로 줄여 판독하므로 1080p 이상이면 충분. 실제로 받은 해상도를 기록해 기종별로 확인 |
| 방향 | 카메라 화면에서 그린 사진은 회전 정보 없이 똑바로 그려짐. 가로·세로 촬영 모두 실기기에서 확인 |
| 접속 | 카메라는 HTTPS에서만 열림. 개발 중에는 `localhost`만 예외 |
| 권한 | 아이폰에서 홈 화면에 추가해 실행할 때 카메라 권한 요청이 반복되는 경우가 있어 실기기로 확인. 권한을 거부하면 촬영 대신 담당자 연락 안내 |

## 3. 검출 도구

모두 브라우저에서 돌아가는 공개 사전 학습 모델입니다. 따로 학습하지 않습니다.

| 대상 | 모델 | 실행 | 크기 |
|---|---|---|---|
| 얼굴 | YuNet (`yunet_web/face_yunet_s_dynamic.onnx`, 서버와 같은 모델) | ONNX Runtime Web | 230KB |
| 번호판 | open-image-models 번호판 모델의 작은 버전 (`yolo-v9-t-*-license-plate-end2end`) | ONNX Runtime Web | 7.8MB |
| 차량 (안전망) | MediaPipe Object Detector의 EfficientDet-Lite0 (COCO 사전 학습, float16) | MediaPipe Tasks Vision (웹) | 7.3MB |

**얼굴:** 서버와 같은 YuNet을 씁니다. 길거리 사진처럼 멀리 있는 작은 얼굴을 잘 찾고 파일이 매우 작습니다. 브라우저용 검출 코드, 입력 크기를 가변으로 바꾼 모델, 시험 사진과 서버 기준 기대 결과가 [yunet_web/](yunet_web/README.md)에 있습니다. 서버 모델 파일(640×640 고정)을 그대로 쓰면 사진을 640으로 줄여야 해 작은 얼굴을 놓치므로 반드시 가변 모델을 씁니다. 구현한 뒤 `node verify.mjs`로 서버와 같은 얼굴을 찾는지 확인합니다. MediaPipe Face Detector(웹)는 가까운 얼굴용 모델이라 멀리 있는 얼굴을 놓치기 쉬워 쓰지 않습니다.

**번호판:** 서버는 큰 모델(`yolo-v9-s-608`, 28.6MB)을 쓰지만 휴대폰 브라우저가 내려받기에는 무거워 작은 버전(7.8MB)을 씁니다. 작은 버전은 입력 크기(256~640)에 따라 성능 차이가 큽니다. 합성 번호판 점검에서 `t-384`는 32%, `t-640`은 4%를 가렸습니다(서버 모델 39%). 합성 점검은 참고용이므로, **어느 입력 크기를 쓸지는 실제 사진 평가로 AI 담당이 정해 파일을 넘깁니다.** 출력은 NMS까지 끝난 `[개수, 7]` 형식이라 후처리가 간단합니다. 글자 인식(OCR)으로 번호판을 찾는 방식은 브라우저에서 한글 인식이 약해 쓰지 않습니다.

- **전처리는 open-image-models와 같게 합니다:** 비율을 유지해 줄이고 남는 곳은 회색(114)으로 채움, RGB 순서, 0~1로 나눔, 점수 기준 0.15(서버 `PLATE_PRETRAINED_CONF`). 캔버스로 줄일 때 `imageSmoothingQuality`를 `"low"`(선형 보간)로 둡니다. `"high"`로 두면 서버(OpenCV 선형 보간)와 점수가 달라져, 합성 번호판 6장 중 점수가 낮은 1장을 놓쳤습니다. `"low"`로 맞춘 뒤 6장 모두 Python 기준 구현과 같은 상자를 찾았습니다(IoU 0.96~1.00).
- **번호판일 수 없는 상자는 버립니다 (2026-10-12 결정):** 작은 모델은 보도 점자블록 같은 노란 직사각형 무늬를 **사진 전체 크기의 번호판**(점수 0.41)으로 잡기도 합니다. 그대로 가리면 사진 전체가 회색이 되어 AI가 "흐림"으로 재촬영을 요구합니다. 그래서 앱은 아래 상자를 버립니다. 버린 것 중 진짜 번호판이 있어도 서버가 큰 모델로 한 번 더 가립니다. 서버의 큰 모델은 같은 사진에서 아무것도 잡지 않아 서버에는 이 규칙이 없습니다.
  - 사진 넓이의 25% 이상인 상자 (점검 사진에서 번호판이 그만큼 크게 찍히지 않음)
  - 가로가 세로의 1.3배보다 좁은 상자 (한국 번호판은 가로가 세로의 약 2~4.7배)

**차량 안전망:** 자동차·버스·트럭·오토바이를 찾았는데 그 안에서 번호판 모델이 번호판을 하나도 못 찾았으면, 차량 전체를 얼굴과 같은 방식으로 거칠게 뭉갭니다. (서버는 규칙 기반 검출기도 함께 쓰지만, 오탐이 많아 그 결과로는 차량 가림을 끄지 않습니다.) 작은 번호판 모델이 놓쳐도 번호가 남지 않게 하는 장치로, 서버도 같은 규칙을 씁니다. 점검 사진에서 차량은 배경이라 가려도 판독에 지장이 적습니다.

**모델 파일 전달과 보관**
- AI 담당이 모델 파일과 입출력 형식, 시험 사진·기대 결과를 버전과 함께 넘깁니다. 앱은 같은 도메인의 버전이 붙은 경로(`/models/<이름>@<버전>.onnx`)로 제공합니다.
- 서비스 워커로 모델 파일을 캐시합니다. 순회 전 오프라인 패키지를 받을 때(`SYN-03`) 모델도 함께 받아 두고, 모델이 준비되지 않았으면 "준비 완료"로 표시하지 않습니다.
- **파일 이름의 버전만 믿지 않습니다.** 같은 이름으로 파일만 바뀌면 서비스 워커가 옛 모델을 계속 씁니다. 모델 주소에 내용 해시를 붙여(예: `face_yunet_s_dynamic@1.onnx?v=98473ed6405c`) 파일이 바뀌면 새로 받게 하고, 같은 모델의 옛 해시 캐시는 지웁니다. 시험용 앱은 서버의 모델 목록(`/pwa/model-manifest.json`)에서 해시가 붙은 주소를 받습니다.
- 모델을 바꾸면 `maskingVersion`을 올립니다. 시험용 앱은 규칙 버전 뒤에 모델 해시를 붙여(`pwa-test-2+e27e5afc`) 모델이 바뀌면 저절로 달라지게 했습니다. 입력 크기·가리는 방법·버리는 상자 규칙을 바꿀 때는 앞의 규칙 버전을 올립니다.

## 4. 가리는 방법

| 대상 | 방법 | 상자 확장 |
|---|---|---|
| 얼굴 | 가로 6칸 정도로 아주 거칠게 모자이크한 뒤 흐림 | 사방 25% |
| 번호판 | 회색(#3C3C3C) 단색으로 덮기 | 사방 20% |
| 번호판을 못 찾은 차량 | 얼굴과 같은 거친 모자이크 + 흐림 | 사방 5% |

캔버스에서는 해당 영역을 아주 작게 줄였다가 `imageSmoothingEnabled = false`로 다시 키우면 모자이크가 됩니다. 흐림에 쓰는 캔버스 `filter`는 브라우저마다 지원이 달라, 지원하지 않으면 모자이크 칸을 더 거칠게 하는 것으로 대신합니다. 약한 흐림이나 잘게 나눈 모자이크는 복원 시도가 가능하므로 서버와 같은 정도로 맞춰 주세요(`privacy.py`의 `_pixelate`, `PLATE_FILL`).

## 5. 원본 다루기

브라우저는 메모리를 직접 지울 수 없으므로, 원본이 **어디에도 옮겨지지 않게** 하는 것이 핵심입니다.

- 원본(가리기 전 캔버스·이미지)은 IndexedDB, Cache Storage, localStorage, 서비스 워커 어디에도 저장하지 않습니다. 기기에 보관할 수 있는 것은 가린 사진뿐입니다.
- 가린 뒤에는 원본 참조를 버립니다. `ImageBitmap.close()`, 원본 캔버스 크기를 0으로, `URL.revokeObjectURL()`.
- 오류 수집·분석 도구(예: 오류 리포트, 화면 기록 도구)에 사진이나 캔버스 내용이 담기지 않게 합니다. 콘솔에도 찍지 않습니다.

## 6. 전송과 오프라인 보관

사진은 업무 백엔드의 사진 제출 API로 올립니다. 경로와 전체 필드는 업무 백엔드 API 명세를 따르고, 마스킹과 관련해 꼭 채울 값은 아래와 같습니다.

| 업무 API 필드 | 값 |
|---|---|
| `deviceMasked` | `true` (앱에서 가렸음) |
| `deviceMaskReport` | `{"faces": 1, "plates": 0, "vehicles": 1, "detector": "yunet+plate-t384+effdet0", "appVersion": "1.0.0"}` |
| `maskingVersion` | 앱 마스킹 규칙의 버전 (모델, 입력 크기, 가리는 방법을 바꾸면 올림) |
| `capturedAt` | 촬영 시각, ISO 8601 |

백엔드는 이 값을 AI 형식(`device_masked`, `device_mask_report`, `app_version`은 snake_case)으로 바꿔 넘깁니다. AI는 운영 설정(`REQUIRE_DEVICE_MASKING=1`)에서 `deviceMasked`가 없는 사진을 받지 않습니다.

**오프라인 보관:** 가린 사진과 제출 ID를 IndexedDB에 영속 저장한 뒤에 다음 장소로 진행합니다. 사진은 Blob이 아니라 **바이트(ArrayBuffer)로 저장**합니다. 아이폰 사파리는 IndexedDB에 Blob을 넣다 실패하는 경우가 있습니다(시험용 앱에서 "저장하지 못했어요"로 재현). 재연결 시 같은 제출 ID로 다시 보내는 방식은 업무 백엔드 API 명세의 오프라인 계약(`SYN-04`, `SYN-05`)을 따릅니다. PWA에서는 다음 두 가지를 함께 지켜 주세요.
- 순회를 시작할 때 `navigator.storage.persist()`로 저장소 유지를 요청합니다. 아이폰은 저장 공간이 부족하면 브라우저 저장소를 지울 수 있으므로, 서버 접수(`RECEIVED`) 전에는 "전송 완료"로 표시하지 않고 대기 건수를 화면에 보여 줍니다.
- 앱을 닫으면 백그라운드 전송이 보장되지 않습니다. 앱을 다시 열 때와 복귀 전에 대기 사진을 전송합니다.
- 같은 사진을 동시에 두 번 보내지 않습니다. 방금 찍은 사진을 보내는 중에 연결 복구로 대기 사진 전송이 시작되면 같은 사진이 겹칠 수 있으므로, 보내는 중인 제출 ID는 그 전송 결과를 함께 기다립니다.
- "전송 대기"로 다음 장소에 보낸 사진이 나중에 재촬영(`RETAKE`)으로 판정되면 그 장소를 다시 찍으라고 알립니다. 이미 끝난 구도(`409 SLOT_RESOLVED`)는 최종 답이므로 대기함에서 뺍니다. 형식 오류(4xx)로 거절된 사진은 자동으로 다시 보내지 않고, 담당자가 지울 수 있게 합니다.

AI는 저장 전 확인에서 앱이 놓친 부분을 가린 수(`server_added`)를 기록합니다. 이 값은 앱 화면에는 오지 않으며, 백엔드가 주 단위로 모아 공유하면 앱 검출기를 보완하는 데 씁니다.

**`server_added` 해석 주의 (2026-10-12 확인, 서버 수정 예정):** 서버는 앱이 이미 가린 영역 안에서도 얼굴을 다시 찾아 셉니다. 모자이크·흐림을 한 얼굴도 YuNet이 얼굴로 보기 때문입니다. 서버가 자기가 가린 사진을 한 번 더 돌려도 얼굴 6개 중 5개를 다시 찾았고, 앱이 가린 같은 사진에서는 4개였습니다(앱 가림이 서버보다 약한 것이 아님). 그래서 지금 값은 "앱이 놓친 수"보다 큽니다. 서버가 이미 가린 영역(모자이크·단색)과 겹치는 검출을 세지 않게 고치기 전까지는, 이 값을 앱 성능으로 보고하지 않습니다. 앱이 놓친 차량은 그대로 셉니다(시험에서 멀리 있는 작은 차 2대를 앱 차량 모델이 놓침).

## 7. 성능 목표와 시험

- **처리 시간:** 저사양 휴대폰 기준으로 촬영 후 전송 준비까지 3초 이내. 시범 참여자가 실제로 쓰는 기종 2~3종(안드로이드 크롬, 아이폰 사파리 포함)에서 직접 재 주세요.
- **실행 방식:** ONNX Runtime Web은 WebGPU를 쓸 수 있으면 빠르고, 없으면 WASM으로 돌아갑니다. WASM 여러 스레드는 페이지에 교차 출처 격리 헤더(COOP/COEP)가 있어야 켜지므로, 배포 설정에 넣을지 측정 결과를 보고 정합니다.
- **첫 실행:** 처음 받는 양은 모델 약 15MB(얼굴 0.2 + 번호판 7.8 + 차량 7.3)와 검출 라이브러리 WASM 약 21MB(ONNX Runtime Web 11 + MediaPipe 9)입니다. 처음 받는 시간과 캐시 후 시간을 따로 잽니다.
- **가림 성공률:** AI 담당이 만드는 라벨 사진 300장(얼굴·번호판 위치 표시)으로, 브라우저에서 돌린 결과를 시험합니다. 목표는 얼굴·번호판 각각 98% 이상입니다.
- **배터리:** 하루 순회(사진 100장 안팎)에서 앱 사용으로 줄어드는 배터리량을 기록합니다.

## 8. 그 밖의 요구사항

- **촬영 사실 표시:** 브라우저 카메라는 기본 카메라 앱과 달리 촬영음이 나지 않습니다. 공개된 장소에서 촬영하는 사업이므로 **앱이 촬영할 때마다 촬영음을 직접 재생**하고, **화면을 하얗게 번쩍여** 조끼·명찰 표시와 함께 촬영 사실을 주변에 알립니다. 아이폰 실기기에서 확인한 점은 다음과 같습니다.
  - 촬영음은 Web Audio가 아니라 `<audio>` 요소로 재생합니다. Web Audio는 무음 스위치를 따라 꺼지고, `<audio>`는 미디어 재생으로 취급돼 무음 모드에서도 납니다. 셔터를 누르는 순간(사용자 동작 안)에 `play()`해야 합니다.
  - **휴대폰 볼륨을 낮추면 웹에서는 소리를 낼 방법이 없습니다.** 아이폰 사파리는 `audio.volume`을 무시하고 현재 볼륨도 알려 주지 않습니다. 그래서 화면 번쩍임을 함께 씁니다.
  - 번쩍임(흰 화면 0.15초 유지 후 0.45초에 걸쳐 사라짐)은 **화면에 실제로 그려진 뒤에 가리기 계산을 시작**해야 보입니다. 가리기 계산(WASM)이 화면 그리기를 1~3초 막아, 바로 시작하면 번쩍임이 그려지지 않고 끝납니다. 촬영 화면을 먼저 캔버스에 잡고, 번쩍임 → 두 번의 `requestAnimationFrame` + 0.25초 → 가리기 순서로 합니다.
  - 번쩍임은 매번 새 애니메이션(`element.animate`)으로 재생합니다. CSS 클래스를 뺐다 붙이는 방식은 아이폰 사파리에서 두 번째 촬영부터 재생되지 않았습니다.
  - 네이티브 앱(React Native 등)은 시스템 카메라 셔터음을 쓸 수 있습니다. 한국 판매 아이폰은 이 소리를 무음 모드·볼륨과 관계없이 냅니다.
- **위치 기록 최소화:** 촬영할 때의 위치만 보냅니다. 이동 경로를 계속 기록하지 않습니다.
- **수리 확인·재점검 촬영:** 이전 사진을 카메라 화면 위에 반투명하게 겹쳐 보여 줍니다. 같은 위치·각도로 찍혀야 AI의 전후 비교가 정확해집니다. 겹쳐 볼 사진은 업무 백엔드가 내려주는 승인된 가린 사진만 쓰고, 받을 수 없으면 겹쳐 보기 없이 찍습니다.
- **어르신 화면에는 판독 결과를 띄우지 않습니다.** 이상 여부·판독 근거는 담당자 화면에만 있고(위험도 등급은 어느 화면에도 표시하지 않음), 어르신 화면에는 업무 백엔드가 내려주는 재촬영·진행 안내만 표시합니다.

## 9. 시험용 앱으로 확인한 것 (2026-10-12)

이 안내서대로 만든 시험용 앱([PWA](../../tools/ai-verify/pwa/README.md), [React Native](../../tools/ai-test-app/README.md))으로 PC 크롬과 아이폰(iOS 26.6, Expo Go 57)에서 확인한 내용입니다. 실제 시니어 앱을 만들 때 참고합니다.

| 항목 | 결과 |
|---|---|
| 얼굴 검출 | 브라우저에서 `yunet_web` 시험 사진 5장 모두 서버와 같은 얼굴. 1920×1080 한 장 약 0.17초(PC) |
| 번호판 검출 | 합성 번호판 6장 모두 Python 기준 구현과 같은 상자 (3장의 전처리 조건) |
| 처리 시간 | 1920×1080 촬영 한 장: 검출·가림·JPEG 합계 약 0.6초(PC, WASM 1스레드). 저사양 폰 3초 목표는 실기기 측정이 남음 |
| 오탐 | 보도 점자블록 사진에서 번호판 오탐 → 3장의 상자 거르기 규칙 추가 |
| 놓침 | 멀리 있는 작은 차 2대를 앱 차량 모델(EfficientDet-Lite0)이 놓침. 서버가 가림. 가림 성공률 300장 평가로 따로 확인 필요 |
| 원본 | 촬영 캔버스는 가린 직후 크기 0. 대기함·캐시에는 가린 JPEG만 |
| 오프라인 | 연결이 끊긴 채 찍으면 대기함에 남고, 연결이 돌아오면 같은 제출 ID로 자동 재전송됨 |

**React Native로 만들 때**
- ONNX Runtime·TFLite 네이티브 모듈은 Expo Go에 없어 개발 빌드가 필요하고, 아이폰에 설치하려면 유료 Apple 개발자 계정이 필요합니다. 시험용 앱은 이를 피하려고 앱 안 보이지 않는 WebView에서 이 안내서의 웹 마스킹 코드를 그대로 돌립니다(`/pwa/mask-host.html`). 카메라 원본은 앱 캐시 임시 파일로만 생기고 가린 직후 지웁니다.
- Expo SDK 57의 `fetch`는 React Native 방식의 파일 첨부(`{uri, name, type}`)를 받지 않습니다("Unsupported FormDataPart implementation"). `expo-file-system`의 `File` 객체를 그대로 `FormData`에 넣습니다.
- Expo Go는 서명된 앱 정보만 받으므로 개발 서버의 Expo 계정 로그인과 프로젝트 등록이 필요하고, 앱 코드 주소가 `https://`여야 iOS가 받습니다. 절차는 [AI 실행 가이드 8장](../../docs/AI_실행_가이드.md#8-휴대폰-시험용-앱-실행하기).
