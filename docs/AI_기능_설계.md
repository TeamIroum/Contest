# AI 기능 설계 — 개발 기준과 연동 조건

정리일: 2026-10-10. 사용자가 제시한 네 기능을 반영한 목표 설계이며, 구현·정확도 검증 완료를 의미하지 않는다. 이전 문서의 '전후 비교는 사람이 수행' 방침은 이 문서의 AI 비교 지원 + 사람 최종 확인 제안으로 변경한다. 실제 담당 범위와 시연 포함 여부는 별도 합의한다.

AI 모듈의 API_CONTRACT.md·README.md를 받은 뒤 구체적인 변환·미지원 기능을 [AI_연동_계약.md](AI_연동_계약.md)에 정리했다. 제공 문서에 analyze/verify/report 기능이 기술되어 있으나 코드·실제 서버·정확도는 검증하지 않았다. 업무 API는 [API_명세서.md](API_명세서.md) v1.0를 따른다.

## 1. 촬영 단계 개인정보 마스킹

- 앱은 휴대폰 안에서 얼굴·차량 번호판을 탐지하고 가린 사진만 업로드한다.
- 가리지 않은 원본은 서버·AI 서비스·분석 도구·오류 수집 등으로 전송하지 않는다. 이 원칙은 별도 검증이 필요하다.
- 휴대폰 마스킹 실패 시 원본 업로드로 우회하지 않는다. 재촬영 또는 실패 안내를 제공한다.
- 서버는 수신 사진을 메모리에서 다시 검사하고 추가 마스킹한다. 최초 검사 전 바이트는 S3·로컬 디스크·프록시 임시 파일에 저장하지 않는다.
- 서버 검사 완료 사진만 판독·관리자 조회·보고서에 제공한다. 재검사 실패 사진은 일반 조회와 판독에 사용하지 않는다.
- 서버 검사 완료본의 보관·삭제와 접근 권한을 정한다. AI의 사후 재마스킹·보류가 업무 저장본에도 전파되도록 사진 버전 계약을 추가한다. 위치·촬영 시각은 필요한 필드로 전달하고 불필요한 EXIF는 제거한다.
- 담당자는 표본과 오류 의심 사진의 마스킹 상태를 확인한다. 자동 마스킹이 모든 개인정보를 완벽히 제거한다고 표현하지 않는다.

## 2. 시설·이상 판독과 부서 배정

- 대상 5종: 보도블록, 빗물받이, 벤치, 안전펜스, 운동기구.
- 사진 품질은 두 단계로 확인한다. 흐림·어두움은 AI를 부르기 전에 일반 코드(OpenCV)가 1초 안에 잡아 재촬영으로 돌려보내고, 이때 사진은 저장하지 않는다(`ai/quality.py`). 판독 대상이 틀 밖에 있거나 시설이 보이지 않는 경우만 AI가 판단한다.
- AI: 틀 밖·시설 안 보임 판단, 시설 종류, 이상 유형, 판독 근거·불확실성.
- AI 모듈이 내는 위험도 등급(`grade`)과 등급에서 나오는 처리 제안(`action`)은 업무에 쓰지 않는다. 원문 결과 스냅샷에만 보관하고(수리 확인 호출의 `prior_json.severity` 입력용), 화면·판정·알림·우선순위에는 쓰지 않는다. AI 계약은 바꾸지 않는다(2026-10-11 결정).
- 백엔드: 배정 시설 ID에 결과 연결, 허용 값 검증, 시설 대장 기준 부서 배정, 이력 저장. 제공 AI가 이미 적용한 위치 가중치를 다시 더하지 않는다.
- 시설 종류만 같다고 동일 시설로 취급하지 않는다. 촬영은 배정된 시설 ID·순회 장소 ID에 연결한다.
- 도로·하수·공원 담당은 예시 분류이며 실제 조직과 매핑은 운영기관과 정한다.
- 불확실·대상 불일치는 검토 대기, 품질 불량은 재촬영으로 구분한다.
- 결과는 사진상 이상 판단이며 전문적인 시설 안전 보장을 의미하지 않는다.

## 3. 전후 비교와 변화 감시

- 앱은 이전에 마스킹한 사진을 촬영 화면에 흐리게 겹쳐 표시해 구도 재현을 돕는다.
- 서버는 시설 ID로 비교 후보를 제한하고, AI는 사진 속 대상과 구도가 비교 가능한지 추가 확인한다. GPS만으로 동일 시설을 확정하지 않는다.
- AI 결과: 수리 확인 제안 / 미수리 의심 / 악화 의심 / 비교 불가.
- 각도·조명·가림 등으로 비교가 어려우면 수리됨 또는 미수리로 강제 판정하지 않는다.
- 백엔드는 재촬영 작업, 재요청 후보, 우선순위 조정과 근거 이력을 관리한다.
- 수리 종결과 재요청 확정은 담당자가 근거 사진·AI 결과를 확인해 수행한다. AI close_case/re_request는 제안으로 저장한다. 현재 보수 회차·증거를 검증하고 과거 요청으로 종결하지 못하게 한다.

## 4. 활동 기록·주간 보고

- 서버가 조별 순회, 실제 참여자, 시설별 촬영·분석·처리 이력을 저장한다.
- 조원 한 명만 촬영해도 조원 각자의 출결과 참여 기록을 별도로 유지한다. 사진 수만으로 개인 활동시간을 산정하지 않는다.
- 사진 수, 점검한 고유 시설 수, 사건 수, 긴급 알림 수를 구분하여 중복 집계하지 않는다.
- 숫자는 DB 집계로 확정하고 AI는 확정된 집계값으로 설명 문장을 작성한다.
- 보고 기간·집계 기준을 명시한다. 검토 대기와 수리 확인 제안을 최종 확정 결과와 구분한다.

## 역할 분담 제안

| 영역 | 책임 |
|---|---|
| 앱 | 카메라, 기기 내 마스킹 실행, 원본 전송 차단, 이전 사진 겹쳐 보기, 업로드·재촬영 안내 |
| AI 담당 | 마스킹 모델 지원, 서버 재검사, 품질·시설·이상 판독, 전후 비교, 보고서 문장 생성 |
| Java/Spring Boot 백엔드 | 사진 처리 상태·접근 제어, 분석 연계, 시설·순회 연결, 배정 규칙, 재점검·처리 이력, 집계 |
| 운영 담당자 | 불확실 결과 검토, 마스킹 표본 점검, 처리·수리 확인 최종 판단 |

제공 모듈 문서는 서버 마스킹·판독·비교·보고 기능을 기술한다. 앱 기기 마스킹, 참고/보수 사진의 개인정보 단독 검사, 이미지 보류 전파, 업무 DB 집계 기반 보고 스키마는 별도로 연결·검증해야 한다.

## 상태 흐름 제안

촬영 → 기기 내 마스킹 → 업무 백엔드 접수 예약 → AI /analyze 통합 호출 → 검사 완료 사진 영속 저장·결과 커밋 → 결과 안내. 제공 모듈은 흐림/어두움을 저장 전에 거절할 수 있어 사진 없는 실패 시도도 기록한다. HTTP 200 + status:error는 접수 성공이 아니다.

수리 확인 촬영에는 이전 사진 겹쳐 보기와 전후 비교를 추가한다. 각 단계 실패를 구분하고 원본 업로드나 정상 판정으로 우회하지 않는다.

## 시연 전에 확인할 사항

- 실제 촬영 앱 방식과 기기 내 마스킹 실행 가능 여부.
- 네 기능 중 10월 15일까지 실제 구현할 기능과 모의 시연 기능.
- 기기 내 마스킹 검증이 안 되면 '원본이 기기 밖으로 나가지 않는다'는 구현 완료 주장을 하지 않는다.
- 기존 마스킹 이미지 업로드는 대체 시연으로 가능하지만 기기 내 자동 마스킹 구현 증거와 구분한다.
- 전후 비교의 사람 승인 범위와 실제 AI 담당 범위.
